# AGENTS.md — обязательные правила проекта «GitConverter»

Эти правила обязательны к исполнению в каждом сеансе работы над проектом.

## Правило 1. Обновление текущего состояния проекта (после получения задания)

После получения задания — сначала обновить и зафиксировать актуальное состояние проекта по теме задачи:

- **в 1С** (рабочая база `localhost\GitConv`) — значения ключевых объектов/реквизитов/констант, имеющих отношение к задаче;
- **в исходниках** (`cfg_src/gitConverter`, при необходимости `cfg_src/MCP_Toolkit_src`) — соответствующие файлы/значения.

Расхождения между базой и исходниками фиксировать и явно указывать в отчёте по задаче.

## Правило 2. Проверка журнала регистрации (в конце каждого состояния/шага)

В конце каждого состояния (шага) работы:

- проверить Журнал регистрации 1С на ошибки (уровни `Error`, `Warning`) за период выполнения шага;
- найденные ошибки разобрать; если они относятся к текущей задаче — исправить до перехода к следующему шагу;
- результат проверки (ошибок нет / перечень ошибок) отражать в отчёте.

## Правило 3. Префикс кастомности имён (`ctm`)

Любые новые имена — реквизиты, измерения, ресурсы, константы, функции/процедуры, объекты метаданных,
команды форм — должны иметь отметку кастомности. В нашем проекте префикс — **`ctm`**:

- реквизит: `ctmИмяРасширения`, `ctmКаталогЗасеваРасширения`;
- константа: `ctmПутьКОнеСкриптНаСервере`;
- метод: `ctmЗагрузитьВерсииХранилища`, `ctmЗаполнитьПользователейХранилища`;
- команда формы: `ctmЗаполнитьВерсииИПользователей`.

Для объектов, созданных до введения правила, префикс добавляется при первой же правке объекта.

## Правило 4. Диагностика зависаний (скриншот)

Если задача не отвечает дольше **одной минуты**, попытаться снять скриншот активного окна
средствами MCP Tools (`get_screenshot`) и проанализировать его (если модель это позволяет):
диалог/модальное окно/зависшее приложение. Результат фиксировать в отчёте.

## Правило 5. Контроль долгой обработки

При подозрении на затяжную обработку (дольше **двух тестовых прогонов**) — дополнительно
анализировать Журнал регистрации на ошибки (см. Правило 2) и логи внешних процессов
(`gitsync.log`, `gitsync_orchestrator.txt` и т.п.).

## Правило 6. Защищённые артефакты — удалять ЗАПРЕЩЕНО

Следующие файлы — рабочие дампы конфигураций 1С. Их **нельзя удалять, перезаписывать, перемещать и
«чистить»** ни при каких уборках временных папок (в том числе при выполнении задач по очистке диска):

- `tools1C\task.cf` — дамп конфигурации рабочей базы (55,9 МБ, 09.09.2026);
- `tools1C\ГитКонверер1Cv8.cf` — дамп конфигурации ГитКонвертер (05.09.2026);
- `tools1C\ГитКонверер1Cv8_0809.cf` — дамп конфигурации ГитКонвертер (08.09.2026).

Файлы помечены атрибутом «Только чтение» (ReadOnly). Полный реестр защищённых артефактов — включая
каталоги, занятые рабочей базой (`E:\rep\task`, `E:\rep\task_git_file210`, `E:\rep\task_temp_file210`) —
ведётся в `docs/ЗАЩИЩЁННЫЕ_АРТЕФАКТЫ.md`. Перед любой задачей на удаление файлов сверяться с этим реестром.

## Правило 7. Расположение документации

Вся проектная документация в Markdown хранится в папке **`docs/`**. В корне остаются только:

- `AGENTS.md` — этот файл правил (Cline читает его из корня автоматически);
- `README.md` — точка входа и навигация по `docs/`.

Новые документы создавать в `docs/` и **регистрировать в навигации** — таблица `docs/` в `README.md`;
краткое описание — в списке документов `docs/memory.md`.

## Правило 8. Раскладка клавиатуры в сообщениях пользователя

Пользователь может набирать текст **в неверной раскладке**. Трактовка:

- символ **`&`** — это **`?`** (в русской раскладке «?» — это `Shift+7`, в английской там `&`):
  сообщение с `&` в конце или в тексте — это **вопрос**, на него нужно ответить, а не игнорировать;
- другие «латинские» знаки в русском тексте читать как соответствующие знаки русской раскладки
  (`&` → `?`, `@` → `"`, `#` → `№`, `$` → `;`, `^` → `:`, `%` → `%`, `.`/`,` — как есть);
- если весь текст выглядит латиницей вместо кириллицы (например, `Ghjtrn` вместо «Проект»),
  это сообщение набрано в английской раскладке: мысленно перевести по клавишам, понять смысл
  и выполнить — переспрашивать не нужно.

При реальной неоднозначности — задать один короткий уточняющий вопрос, но не оставлять сообщение без ответа.

## Правило 9. Клиентские сеансы 1С — открытые и по одному

Если работа идёт с **клиентской частью** (интерактивный режим `1С:Предприятие`: `ENTERPRISE`, `/Execute`,
работа через MCP-1С, проверки в живой базе):

- запускать 1С **с видимым окном** — без `-WindowStyle Hidden`; окно не скрывать (`ShowWindow(SW_HIDE)`
  и «увод в фон» запрещены) — пользователь должен видеть сеанс;
- держать **ровно один** клиентский сеанс на базу. Перед запуском проверить, не поднят ли он уже:
  `Get-Process 1cv8*` и, для `localhost\GitConv`, `http://localhost:6003/health`. Если сеанс есть —
  **использовать его** (в том числе MCP-канал), второй не поднимать; лишние и «висячие» сеансы закрывать;
- для `localhost\GitConv` клиентский сеанс поднимать сразу с `MCP_Toolkit.epf` (автостарт MCP-сервера) —
  это штатный, наиболее удобный канал управления и диагностики;
- путь с пробелами (`E:\project\0509 git converter\…`) в `Start-Process -ArgumentList` передавать
  **в кавычках** — иначе платформа получает обрезанный путь («Файл не обнаружен 'E:\project\0509'»);
- после запуска убедиться, что окно видимо (`IsWindowVisible = True`) и MCP отвечает `healthy`.
  Видимое окно — обязательное условие для скриншотов по Правилу 4.

**Исключение — пакетные (неинтерактивные) режимы:** `DESIGNER` (`/DumpConfigToFiles`, `/LoadConfigFromFiles`,
`/UpdateDBCfg`, `/CheckModules`, `/DumpCfg`, `/DumpIB`), сборка `epf`/`erf`, `ibcmd`, COM-соединение.
Они окна не показывают и не требуют — их оконный режим значения не имеет и на Правило 9 не влияет.

## Рабочие ориентиры

- Рабочая база: `localhost\GitConv`, пользователь `Администратор` (файловое хранилище `E:\rep\task`).
- Клиентский сеанс рабочей базы — **один и видимый** (Правило 9):
  `1cv8.exe ENTERPRISE /S localhost\GitConv /N Администратор /Execute "E:\project\0509 git converter\MCP_Toolkit.epf"`.
  MCP-1С слушает `http://localhost:6003` (`/health` → `healthy`); обёртка для вызова по HTTP —
  `docs/audit-2026-09-28/mcp_1c_call.ps1` (у `execute_code` результат возвращается через переменную `Результат`).
- Исходники конфигурации: `cfg_src/gitConverter`; обработка: `cfg_src/MCP_Toolkit_src`.
- Платформа: `C:\Program Files\1cv8\8.3.27.2214\bin`.
- База разработки и рабочая — одна: `localhost\GitConv` (в `.v8-project.json` — id `gitconv`, `default`,
  псевдоним `dev`). Отдельной файловой dev-базы нет — для проверок сборки/синтаксиса создаётся временная
  файловая база (например, `%TEMP%\gk_check_ib`) и удаляется после; 1С компилирует модули лениво —
  успешная загрузка НЕ гарантирует отсутствие ошибок компиляции; надёжнее проверять `/CheckModules`
  и Журнал регистрации.
