# Поддержка хранилищ расширений конфигурации (эксперимент 27.09.2026)

> **Стенд:** копия хранилища `E:\rep\_ext_probe\repo` (оригинал `E:\rep\erp25ExtDopFunkcional`
> не изменялся), платформа `8.3.27.2214`, расширение **`ExtDopFunkcional`** (назначение `AddOn`,
> префикс `нов_`, вендор ООО "ИСТК").
> **Повод:** конвейер 1С:ГитКонвертера и кнопка «Получить все версии…» падают с
> «Соединение основной конфигурации с хранилищем расширений конфигураций невозможно» (см. `КОНТЕКСТ_СЕССИИ.md` §16.2).

## 1. Главная находка: позиция ключа `-Extension`

Для команд хранилища ключ `-Extension "<ИмяРасширения>"` работает **только если указан ПОСЛЕ
команды/ключей хранилища**:

| Позиция ключа | Команда | Результат |
|---|---|---|
| перед хранилищем | `… /Extension ExtDopFunkcional /ConfigurationRepositoryReport out.mxl -NBegin 1` | ❌ «Соединение основной конфигурации с хранилищем расширений конфигураций невозможно» |
| **после хранилища** | `… /ConfigurationRepositoryReport out.mxl -NBegin 1 -Extension ExtDopFunkcional` | ✅ **«Отчет успешно построен»** (exit 0) |

Второе обязательное условие: расширение с таким именем **должно уже быть в базе**, иначе —
«Операция не может быть выполнена, так как расширение конфигурации с указанным именем не найдено:
ExtDopFunkcional / Ошибка открытия расширения конфигурации».

## 2. Проверенная матрица команд

Все команды ниже — против **пустой** файловой базы (без основной конфигурации ERP), exit-коды реальные.

| Шаг | Команда | Результат |
|---|---|---|
| Засев расширения из XML-выгрузки | `DESIGNER /F <db> /LoadConfigFromFiles "<dumpDir>" -AllExtensions /UpdateDBCfg` | exit 0; расширение создано (подтверждено `/DumpCfg <f>.cfe -Extension` → 14,33 МБ и `/DumpConfigToFiles <dir> -AllExtensions` → папка `ExtDopFunkcional`) |
| Отчёт по версиям | `… /ConfigurationRepositoryF <repo> /ConfigurationRepositoryN <user> /ConfigurationRepositoryP <pwd> /ConfigurationRepositoryReport "<f>.mxl" -NBegin N [-NEnd M] -Extension "ExtDopFunkcional"` | exit 0; `-NBegin 1` без `-NEnd` → 4,02 МБ; диапазон `1..3` → 0,13 МБ |
| Выгрузка версии из хранилища в `.cfe` | `… /ConfigurationRepositoryDumpCfg "<f>.cfe" -v<N> -Extension "ExtDopFunkcional"` | exit 0, 3,1 с → `v1.cfe` **11,1 МБ** |
| Загрузка `.cfe` в базу | `DESIGNER /F <db> /LoadCfg "<f>.cfe" -Extension "ExtDopFunkcional"` | exit 0, 2,1 с, «Загрузка конфигурации успешно завершена» |
| Выгрузка расширения в XML | `DESIGNER /F <db> /DumpConfigToFiles "<dir>" -Extension "ExtDopFunkcional"` | exit 0, 7,1 с → полный набор (`Catalogs`, `Documents`, … `Configuration.xml`, `ConfigDumpInfo.xml`); всего ~2510 файлов |
| Обновление из хранилища на версию | `… /ConfigurationRepositoryUpdateCfg -v<N> -force -Extension "ExtDopFunkcional" /UpdateDBCfg` | exit 101 в пустой базе («Не найден объект РегистрСведений.…») — **нужна база с основной конфигурацией**; в режиме расширения не требуется, если идти через `DumpCfg → LoadCfg → DumpConfigToFiles` |
| Создание расширения (альтернатива засеву) | `ibcmd extension create --name ExtDopFunkcional --name-prefix <префикс> --purpose add-on` | есть в `ibcmd` (8.3.20+), не проверялось |

**Ключевой вывод.** Цепочка «хранилище расширения → XML-файлы версии» работает в **пустой** временной
базе, если расширение в неё засеяно. Тяжёлая база с ERP и шаг `UpdateCfg/UpdateDBCfg` не нужны:
их заменяют `ConfigurationRepositoryDumpCfg -vN` + `LoadCfg` + `DumpConfigToFiles`.

## 3. Что НЕ работает (проверено — не повторять)

- `/Extension` **перед** ключами хранилища — ключ игнорируется (с заведомо несуществующим именем
  ошибка та же).
- `/ConfigurationRepositoryBindCfg -Extension …` → «Подключение основной конфигурации к хранилищу
  расширений конфигураций невозможно»; **bind расширения через командную строку не поддерживается**.
- `/ConfigurationRepositoryCreate` → «Создание хранилища конфигурации завершилось с ошибкой».
- `ibcmd config` — операций с хранилищем нет вообще (только load/save/check/apply/reset/repair/
  export/import/extension/generation-id/sign).
- Штатный `1C-Company/GitConverter` конвертирует только основную конфигурацию; `v8runner` не умеет
  загрузку расширения из его хранилища (открытый issue #148); `gitsync`/`tool1cd` на таком хранилище
  падает (issue #211).

## 4. План внедрения

1. Реквизит справочника `ХранилищаКонфигураций` → **`ctmИмяРасширения`** (Правило 3). Заполнен →
   конвейер работает в режиме расширения (пока — только по этому реквизиту, без автоопределения).
2. Засев расширения во временную базу перед первым отчётом (`ibcmd extension create` или
   `/LoadConfigFromFiles <dumpDir> -AllExtensions`).
3. Во все шаблоны команд конфигуратора добавить `-Extension "<имя>"` **в конец** команд хранилища,
   а также в файловые команды (`/LoadCfg`, `/DumpConfigToFiles`).
4. Для режима расширения заменить пару `ConfigurationRepositoryUpdateCfg + /UpdateDBCfg` на
   `ConfigurationRepositoryDumpCfg -vN` + `LoadCfg`.
5. Кнопка «Получить все версии и заполнить пользователей» — тот же ключ в команде отчёта.
6. Попутно исправить «немую» ошибку в `КонвертацияХранилища`, строка 3361:
   `СтрШаблон(НСтр("ru = '…'", Параметры.ИмяФайлаЛогов))` — вторым параметром `НСтр` вместо кода языка
   передаётся путь, поэтому текст ошибки теряется (и в ЖР, и в сообщении формы).

## 5. Открытые вопросы

- Общее число версий в хранилище (для оценки времени прогона) — уточнить отчётом/парсером
  `ВерсииХранилища.ЗагрузитьВерсииИзОтчета`.
- Достаточно ли `ibcmd extension create` без XML-затравки (префикс/назначение расширения).
- Нужно ли применять расширение (`/UpdateDBCfg`) для отчёта и выгрузки в XML — по эксперименту не нужно
  (отчёт и `DumpConfigToFiles` работают с конфигурацией расширения, а не с данными БД).
- Формат коммитов и раскладка git-репозитория для расширения — предполагаем как для основной
  конфигурации.
