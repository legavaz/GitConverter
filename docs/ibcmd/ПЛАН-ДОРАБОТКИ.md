## Блоки работ

### A. Исправить неверную документацию — ~0,5 ч

Формулировки вида «ibcmd поддерживает только файловые базы» / «не поддерживает серверные» сейчас
некорректны как утверждение о возможностях утилиты. Заменить на точную формулировку в `SKILL.md`
и docstring'ах 13 скиллов + в комментариях ibcmd-веток:

> Скиллы ограничивают `ibcmd` файловой базой **намеренно**: в offline-режиме `ibcmd` поднимает собственный
> автономный сервер против СУБД, поэтому базу, которую держит живой кластер, отдавать под второй движок
> нельзя. Полный набор параметров подключения к СУБД — вендор, Приложение 4, разд. 4.10.2
> (`--dbms`, `--db-name`, `--db-server`, `--db-user`, `--db-pwd`, `-W`, а также `--pid` / `--remote`
> для работающего автономного сервера).

Затронуть: сообщения об отказе (15 мест), комментарии `# --- ibcmd branch (file infobase only) ---`,
`db-cfe-admin.ps1:725` / `.py:812`.

### C. Дозакрыть ibcmd-ветки существующих скиллов — ~3–4 ч

| Скилл | Что сделать | Оценка |
|---|---|---|
| `db-dump-xml` | Реализовать `Mode UpdateInfo` через `config export info --out=` и `--base/--sync/--force` **вместо отказа** (`db-dump-xml.ps1:590`). Выставить `-Threads`, `-Archive`, `-IgnoreUnresolvedRefs` | 1,5 ч |
| `db-update` | Новые параметры для `--session-terminate=<disable\|prompt\|force>` и `--session-terminate-message`; задокументировать, что `-Server` и `-WarningsAsErrors` для ibcmd неприменимы | 0,5 ч |
| `db-load-xml` | Маппинг `-NoApplyCheck` → `import --no-check`; выставить `--archive`, `--base-dir` | 0,5 ч |
| `db-create` | Выставить `-Locale` → `--locale`; задокументировать `--date-offset` | 0,25 ч |
| `db-cfe-admin` | Добавить `config extension info --name=<x>`; уточнить формулировку ограничения (после A) | 0,5 ч |
| `db-list` | Описать в `SKILL.md` ключ `ibcmdargs`; подготовить (но не вводить) место под блок ibcmd-соединения | 0,25 ч |

Обязательное условие: **каждая правка — в обе реализации** (`.ps1` и `.py`), они синхронны по поведению.

### B. Серверные базы через `--dbms` / `--pid` / `--remote` — ~4–6 ч — ОТЛОЖЕНО

Что потребуется, когда вернёмся к вопросу:

1. Общий хелпер построения ibcmd-аргументов подключения (сейчас логика продублирована в 13 скиллах —
   править её в каждом отдельно дорого; имеет смысл вынести).
2. Параметры: `-Dbms`, `-DbUser`, `-DbPassword`, `-IbcmdPid`, `-IbcmdRemote`; переиспользовать
   `-InfoBaseServer`/`-InfoBaseRef`/`-UserName`/`-Password` как `--db-server`/`--db-name`/`--user`/`--password`.
3. **Предохранитель**: путь через `--dbms` — только с явным согласием (`-AllowSharedServerDb`) и предупреждением
   про два движка на одной базе; путь через `--pid`/`--remote` (работающий автономный сервер) считать
   безопасным и дополнительного флага не требующим.
4. Убрать 15 запретов и обновить `argHints` (сейчас `--db-path` → `-InfoBasePath`).
5. Отдельно решить судьбу ограничения «свойства расширений только для файловой базы» в `db-cfe-admin`.

### D. Новые скиллы — ~6–8 ч, по приоритету

| № | Скилл | Накрывает | Оценка |
|---|---|---|---|
| 1 | **`db-eventlog`** | `ibcmd eventlog export` — Журнал регистрации без MCP (Правило 2 AGENTS.md). Параметры команды уточнить по стр. 68 вендорского документа | 1,5 ч |
| 2 | **`db-session`** | `session info/list/terminate/interrupt-current-server-call`, `lock list` — «лишние и висячие сеансы закрывать» из Правила 9 без MCP. ⚠️ только работающий автономный сервер | 2 ч |
| 3 | `db-repair-config` | `config repair --commit/--rollback/--fix-metadata`, `config reset`, `generation-id` | 1,5 ч |
| 4 | `db-migrate` | `server config init`, `server config import` (из реестра кластера), `infobase replicate` | 2 ч |
| 5 | `db-sign` | `config sign`, `mobile-client sign` | 1 ч |
| — | `support-edit` (доработка, не новый) | путь `config support disable --force` вместо Конфигуратора | 0,5 ч |
| — | `db-cfe-admin` (доработка) | `extension create`, `extension delete --all` | 0,5 ч |

⚠️ Все режимы `session` / `lock` вендер разрешает **только** при подключении к работающему автономному
серверу. Для кластерных баз проекта это означает, что `db-session` окажется применим лишь к файловым базам
и к ibsrv — приоритет у него ниже, чем кажется, реализовывать после `db-eventlog`.

## Порядок реализации и контрольные точки

1. **A** → правка формулировок, без запуска кода.
2. **C** → каждый скилл: правка `.ps1` + `.py`, прогон на временной файловой базе (`%TEMP%\gk_check_ib`),
   проверка Журнала регистрации (Правило 2) после каждого скилла.
3. **`db-eventlog`** → новый скилл по образцу существующих (SKILL.md + `scripts/×.ps1` + `scripts/×.py`).
4. **`db-session`** → то же; проверить ограничение «только работающий ibsrv» на практике.
5. Документация: новые файлы — в `docs/` с регистрацией в таблице README.md и в списке `docs/memory.md` (Правило 7).

## Риски

| Риск | Митигация |
|---|---|
| Расхождение поведения `.ps1` и `.py` после правок | Править обе реализации в одной правке; проверять обе |
| Проверка только на одной платформе | Установлена `8.3.27.2214`; при смене платформы — перепроверка (ibcmd не во всех установках) |
| Ошибка в маппинге `--force` / `--dynamic` / `--session-terminate` | Сверяться с [ВЕНДОР-IBCMD-4.10.md](ВЕНДОР-IBCMD-4.10.md) §6.1; расхождение `--force` описано в [МАТРИЦА-РАСХОЖДЕНИЙ.md](МАТРИЦА-РАСХОЖДЕНИЙ.md) §4 |
| Попытка применить `db-eventlog` к базе кластера | `eventlog export` требует ibsrv; для кластерных баз — MCP `get_event_log` |
