## [2026-09-28] ИСПРАВЛЕНО: галочка «Выгружать изменения» (частичная выгрузка)

**Симптом.** Флаг `ВыгружатьИзменения` у `task` = Да, но фактически всегда выполнялась **полная**
выгрузка: `-update -getChanges` не создавал файлы, движок падал в полную выгрузку (`ВыгрузкаИзменений`
у всех версий = Ложь), `dump` — всегда тысячи файлов.

**Причина (экспериментально подтверждена).** Ключ конфигуратора `-getChanges` формирует **только файл-список**
изменений (`diff.txt`), а сами файлы объектов в каталог выгрузки **не кладёт**; движок, видя 0 файлов,
делал откат на полную выгрузку. Частичную выгрузку в файловой/серверной базе выполняет ключ
`-update -configDumpInfoForChanges <PrevState>` (без `-getChanges`) — он обновляет `ConfigDumpInfo.xml`
и выгружает только изменившиеся объекты.

**Правка (`CommonModules/КонвертацияХранилища`):**
- `ВыгрузитьКонфигурациюВФайлы`: новая ветка `ВыгружатьТолькоИзменения` → `-update -force -configDumpInfoForChanges`
  (без `-getChanges`); ветка с `-getChanges` сохранена только для EDT;
- `ВыгрузитьВерсию`: для не-EDT режима ставится флаг `ВыгружатьТолькоИзменения`, `diff.txt` не требуется;
  признак `ВыгрузкаИзменений` выставляется для не-EDT без чтения `diff.txt`.

**Проверка на бою (прогон 232–251, репозиторий `task_git_file211`):** версии 248, 249, 250, 251 —

250 — 7, 251 — 5). Выгрузка версии 248 заняла ~2 с (против ~9 с при полной). `ConfigDumpInfo.xml`

**Примечание.** `ConfigDumpInfo.xml` внесён в `.gitignore` репозитория (не отслеживается git, но

1. Уборка была **неявным побочным эффектом** записи объекта версии (`ВерсииХранилища.ПриЗаписи` →
   `УдалитьФайлыВерсииВФоне`) и **не была привязана к коммиту**. Периодическая проверка
   `ПроверитьУдалениеВременныхДанныхВерсийПослеКоммита` вызывается только в начале `ВыполнитьКонвертацию`
   (после проверки `ОстановитьКонвертацию`), поэтому при выключенном регламентном задании «хвост» не удалялся.
2. Ограничение выборки `ПЕРВЫЕ 10` — большой массив не разгребался за один проход.
3. **«Осиротевшие» каталоги.** При сбросе версии ссылка `КаталогВременныхФайлов` очищалась **без удаления
   файлов** (`ПроверитьПолученныеВерсии`), а `ОбнулитьДиапазонВерсий` чистил только `dump`, оставляя `db`.
   Штатная уборка ищет каталоги только по заполненной ссылке → такие каталоги не удалялись никогда
   (пример — `E:\rep\task_temp_file210\121`).

**Что сделано (код).**
- `ВыполнитьКоммиты`: добавлен **явный пункт удаления сразу после присвоения версии состояния
  «Версия помещена»** (по флагу; реквизит добавлен в структуру чтения хранилища). Не зависит от
  следующего запуска конвейера.
- `ПроверитьУдалениеВременныхДанныхВерсийПослеКоммита`: `ПЕРВЫЕ 10` → `ПЕРВЫЕ 100`; в журнал пишется
  число запущенных удалений.
- `УдалитьФайлыВерсии`: успех/ошибка журналируются (раньше сбой глушился `Попытка` без следа);
  при ошибке каталог остаётся заполненным для повторной попытки.
- Модуль объекта `ВерсииХранилища`: неявный триггер удаления из `ПриЗаписи` **убран** — удаление только явное.
- `ПроверитьПолученныеВерсии` и `ОбнулитьДиапазонВерсий`: файлы удаляются **до** очистки ссылки.

**Проверка на бою.** Включён флаг у `erp25` → уборка 857–862: каталоги удалены за ~30 с, освобождено
**+22,6 ГБ** (208,8 → 231,4 ГБ), в журнале 6 записей `КХ.УдалениеВременныхДанныхВерсии.Выполнено`,
состояния/хеши версий не изменены. Включён флаг у `task` → удалено 22 из 23 каталогов (1,35 ГБ);
остался `121` (осиротевший до правки — удалить вручную). `/CheckModules` — «Синтаксических ошибок
не обнаружено!». Журнал регистрации — без ошибок/предупреждений.

**Рекомендации.**
1. Держать `УдалятьВременныеДанныеВерсииПослеКоммита = Истина` для хранилищ с крупными версиями
   (erp25 — 3,8 ГБ/версия), иначе диск растёт линейно.
2. Частичная выгрузка при этом **не страдает**: `ConfigDumpInfo` предыдущей помещённой версии берётся
   из git (`src\ConfigDumpInfo.xml`), а не из удаляемого каталога.
3. `DumpFilesIndex.txt` / `ConfigDumpInfo.xml` сейчас в `.gitignore`: при частичной выгрузке индекс
   не копируется в `src`, из-за чего индекс предыдущей версии может устареть (отдельный дефект, бэклог).
4. Старые «осиротевшие» каталоги (например, `task_temp_file210\121`) после правки не создаются,
   но уже существующие удаляются только вручную.
